Platform · Edge

NikTiar™ SecureEdge

A dedicated next-generation edge appliance for one organization — NGFW policies, managed WAF, DNS Filter, URL Filter, and layered ransomware exposure controls — without sending production traffic to an external cloud edge service.

How it works Capabilities Applications supported Who should go for it

How it works

NikTiar SecureEdge sits in front of your public hostnames as a dedicated edge for one organization. Visitor HTTPS terminates on the appliance; clean traffic is proxied to your origin. Optionally, LAN clients can use the same appliance as DNS so known-bad domains are sinkholed before a connection starts.

  1. Onboard a zone — public hostname → origin URL, TLS mode, and security level.
  2. Apply layered policy — NGFW allow/deny rules, URL Filter categories, DNS Filter categories, Ransomware Defense, Security Profiles, WAF, rate limits, and advanced defenses from the SecureEdge operator console.
  3. Cut over public DNS — point each hostname at SecureEdge so visitors hit the edge first.
  4. Optional LAN DNS — point DHCP/DNS at the edge when you want category-based domain sinkholing for workstations.
  5. Operate in Kevantic portals — admins and customers see sites, events, and health in NikTiar portals — not third-party engine consoles.

Dedicated only. Each customer receives their own SecureEdge appliance (virtual or physical form factor as scoped in the engagement). Unknown Host headers are denied; firewall and custom rules stay scoped to each site hostname.

Applications & workloads supported

SecureEdge protects HTTP(S) front doors — any stack that speaks web or API over TLS.

  • Customer & partner portals — React / Vue / Angular SPAs, server-rendered portals, reverse-proxied intranet apps published to the internet
  • Corporate & marketing websites — WordPress, static sites, CMS, brochureware with login or forms
  • REST & JSON APIs — mobile backends, B2B integrations, webhook receivers (API protection: JSON content-type, TRACE block, body size caps)
  • GraphQL APIs — batch / depth / alias guards against abusive query patterns
  • Ecommerce & checkout — cart and payment frontends that need bot and credential-stuffing resistance
  • Login & SSO front doors — auth path rate limits, leaked-credential checks (privacy-preserving lookups), challenge pages during active attacks
  • Ticket / launch / flash-sale sites — Visitor queue queues bursts so origins stay healthy
  • Admin & ops UIs that must be internet-reachable — virtual patches for common CVE paths while IT remediates

Not a fit for pure offline / air-gapped estates with no public HTTP(S), or for non-HTTP protocols (SMTP, industrial OT buses) — those stay with other NikTiar modules.

Capabilities (technical)

  • NGFW policies — ordered Allow / Deny / Challenge / Log rules by IP group, path, method, User-Agent, and application profile
  • Managed web application firewall — common web-attack classes (such as SQLi and XSS) with tunable security level and inspection depth
  • NikTiar URL Filter — HTTP path category controls for malware, phishing, ransomware-related, and scanner-style patterns
  • NikTiar DNS Filter — category feeds and domain blocklists at DNS resolution when clients use this edge as DNS; optional Host-header mirror on the web edge
  • Ransomware Defense — layered controls intended to reduce exposure to known ransomware infrastructure domains and common web-borne dropper / ransom-note / WebDAV abuse patterns (complements endpoint security; does not replace EDR or backups)
  • Security Profiles — File Blocking, Anti-Spyware style host/path heuristics, URL category alignment, and operator-managed threat lists
  • Bot defense, client integrity & rate limits — scrapers, headless clients, login/API flood throttling (HTTP 429)
  • IP / User-Agent / geo firewall & custom WAF rules — Host-scoped so site policies stay isolated on the dedicated edge
  • SSL/TLS modes & optional edge cache — Flexible / Full / Strict; Bypass or Standard cache with edge TTL
  • Advanced defenses — API protection, GraphQL abuse protection, page security headers, visitor queue, virtual path patches, auth hardening, sensitive-data detection (default log), leaked-credential checks, log-export webhooks, honeypot paths, mutual TLS (when CA is wired)
  • Dedicated isolation — unknown Host → HTTP 421; exact Host → that zone’s origin only; no shared multi-tenant fallthrough

Marketing and contracts describe controls and exposure reduction — not a guarantee that ransomware, breaches, or downtime cannot occur.

Deployment model

  • Dedicated SecureEdge — one organization per appliance. Best for regulated estates, high traffic, or contractually isolated edges.
  • Form factor — virtual appliance or physical hardware as scoped with Kevantic for the engagement (resilience design is engagement-specific).

Shared multi-tenant SecureEdge is not offered. Dedicated isolation is the product default.

Who should go for it

  • Security and IT leaders exposing portals, APIs, or ecommerce who need dedicated WAF + NGFW + DNS controls.
  • Buyers who want enterprise edge controls without mandatory traffic exit to an external cloud edge service.
  • Organizations that require a dedicated edge appliance for one customer estate (not a shared multi-tenant edge).
  • Teams already on NikTiar Silver / Gold / Platinum who want the public HTTP edge covered end-to-end.

Usually not the best fit if…

  • You have no public HTTP(S) applications.
  • You only need outside-in discovery — start with EASM; add SecureEdge when you are ready to terminate traffic.
  • You need a global CDN PoP mesh in every country — SecureEdge is an appliance edge, not a hyperscale CDN footprint.

Limitations (honest scope)

  • Protects HTTP(S) edges (and optional LAN DNS) you place behind SecureEdge — not a worldwide CDN PoP mesh.
  • Does not replace endpoint MDR/EDR, NDR, backups, or identity ITDR (those remain NikTiar subscription / complementary controls).
  • Ransomware Defense and DNS Filter help reduce exposure to known infrastructure and common web patterns; they do not guarantee zero ransomware or stop encryption already running on an endpoint.
  • DNS cutover, certificates, LAN DNS pointing, and origin readiness still need an IT change window.
  • Mutual TLS and some advanced toggles need ops wiring (CA / client certificates) on the dedicated edge.
  • WAF and NGFW reduce risk; they do not fix every application business-logic flaw.
